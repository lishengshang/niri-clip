# ADR-002: FTS5 全文索引 tokenizer 选型 trigram

- 状态：已采纳（2026-09-01，任务 2.1）
- 关联：ROADMAP Phase 2 / 2.1（原计划"unicode61 起步，按需评估 simple tokenizer"）

## 背景

任务 2.1 为剪贴板历史库建 FTS5 全文索引（`clips_fts`，外部内容表 + 三触发器
同步）。tokenizer 决定中文搜索的实际效果，建表后更换需重建索引，属一次成型
的选型。

## 决策

采用 SQLite 内置 **trigram** tokenizer。

## 理由

剪贴板历史以中文/混合内容为主。unicode61 把连续中文整句切成单一 token——
搜"剪贴"无法命中"剪贴板历史"，中文子串搜索基本不可用（实测见下）。trigram
以 3 字符滑窗切分，中英文任意子串均命中，且为零额外依赖的内置能力：

- 实测（本机 10k 条混合库）：`fts_search_300_of_10k` ≈0.16ms，预算 <50ms
  的 1/300；中文 3 字短语子串命中验证通过

## 被拒备选

- **unicode61**（ROADMAP 原起步方案）：英文按词可用，中文子串不可用，
  后期大概率被迫二次迁移重建索引
- **simple/jieba 社区 tokenizer**：中文按词命中体验好，但引入 C 依赖违背
  "低开销"产品原则（依赖必须过审计），且索引效果对本场景无决定性优势

## 代价与边界（已验证/已文档化）

- 索引体积约为文本的 2–3 倍（外部内容表不复制正文，仅存 grams）
- <3 字符查询对 trigram 无增益 → `store::search` 退化为
  `clips.text LIKE` 线性扫描（10k 条毫秒级，通配符已转义）
- 标点按字面索引：跨标点短语不命中（如内容 `"inner" text` 搜
  `inner text` 不命中）——符合子串搜索语义，单测锁定
- 更换 tokenizer 需重建：DROP clips_fts → 重建 → 回填（未来若做，走
  `user_version` 新迁移）
