# ADR-004: 历史导出格式 = NDJSON 行式 + 图片内嵌 base64

- 状态：已采纳（2026-09-09，任务 2.4）
- 关联：ROADMAP Phase 2 / 2.4；ADR-003（hash 是本格式的幂等合并键）；
  Phase 5「历史内容动作插件化」——导出格式即扩展点，一旦发布只增不改

## 背景

任务 2.4 要求全量导出/备份（`export --json`）与回灌（`import`）。格式是
长期契约：v1.0 数据可携、外部工具消费、插件化阶段复用，建库后难再改。
三个待定维度：承载形态（单文件 JSON 数组 / NDJSON / 目录包）、图片载荷
（内嵌 base64 / 旁挂目录）、是否附物理快照。

## 决策

**NDJSON**：首行 header（`format`/`version`/`user_version`/`exported_at`/
`count`），随后每行一个条目（`hash`/`text`/`mime`/`ts`/`pinned`/`size`，
图片条目另有 `image_base64`）。图片载荷**内嵌 base64** 自包含单文件；
`export --sqlite <路径>` 以 `VACUUM INTO` 附带产出物理快照作为互补形态。

## 理由

- **流式 = 内存有界**：读写全程按行进行，峰值内存 = 最大单条目（约一张
  10MiB 上限图片），images/ 配额 200MiB 的极端库也不受进程内存牵制。
  这是单文件 JSON 数组做不到的——serde_json 无数组流式迭代器，回灌须
  整体载入（图片库大时数百 MB 峰值）
- **外部工具友好**：每行独立可解析，`grep`/`jq`/`wc -l` 直接可用；
  Phase 5 插件化时逐行消费零门槛
- **字节稳定**：固定 `ts ASC, id ASC` 排序，同库两次导出可 diff
- **内嵌 base64 vs 旁挂目录**：+33% 体积换"单文件即完整备份"——管道、
  拷贝、异地存放都只面对一个文件，符合"简洁"产品原则；体积压力由
  `export - | gzip` 管道化解（未内建压缩，避免再造轮子）
- **--sqlite 互补**：JSON 导出跨版本/跨机器可携 + hash 幂等合并，但不是
  逐字节还原；物理快照保真却绑 schema 版本。两者各司其职，实现成本
  仅一条 `VACUUM INTO`（复用 migrate.rs 既有模式）

## 被拒备选

- **单文件 JSON 数组**（`{header, clips:[...]}`）：最直观的交换格式，但
  回灌必须整体载入内存，违背性能原则的内存纪律
- **目录包**（json + images/ 旁挂按 hash 命名）：零体积膨胀，但单文件
  备份退化成目录搬运，破坏管道与自包含性
- **仅 sqlite 快照**（不做 JSON）：实现最省，但绑版本、无法做幂等合并
  （回灌 = 全量替换或人工 SQL），更堵死插件化的格式扩展点
- **图片只导元数据不导载荷**：验收标准"备份可回灌"不成立

## 代价与边界（已验证/已文档化）

- **导入完整性校验**：每条重算 hash（文本 blake3 / 图片 FNV key）比对，
  损坏或被篡改条目跳过并警告，好条目照常入库；同文件内重复 hash 自然
  收敛（exists 计数）
- **导入原子性**：单 BEGIN IMMEDIATE 事务，图片文件 tmp+rename 与行插入
  同窗口（同 insert_image_with 模式）；硬错误整体回滚
- **时序语义**：回灌保留原 ts 与 pinned，不刷新 ▶ 指针（import 不是捕获）；
  结束按当前配置执行一次 `enforce_max_items`（与捕获路径同一上限语义）
- **权限**：备份是全量剪贴板明文，导出文件 0600；`--sqlite` 目标已存在
  拒绝覆盖（备份命令绝不静默覆盖）
- **依赖闭包**：serde_json 本就是 GUI 直接依赖（workspace 无增量），CLI
  主包经 core 引入 +4（serde_json/itoa/ryu/memchr）+ base64 1（零传递
  依赖），ARCHITECTURE §9 已同步
- **格式演进**：header.version 高于本实现时回灌明确报错提示升级；未来
  只增不改（新字段可选、旧字段不回收）
