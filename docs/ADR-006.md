# ADR-006: 加密存储 PoC 结论——按条目 AEAD 为 v2.0 落地方案

- 状态：已采纳（2026-09-18，任务 3.4 PoC；**实现推迟至 v2.0，本轮仅交付决策文档**）
- 关联：ROADMAP Phase 3 / 3.4、Phase 6（加密历史）；任务 3.1（ignore_regex 阻止
  敏感内容入库）、3.3（`wipe --sensitive` 清除存量）；ARCHITECTURE §1（分层）

## 背景

剪贴板历史是敏感数据聚集地。3.1（默认过滤密码管理器格式）与 3.3（存量清除）
解决的是"敏感内容**不进库 / 及时清走**"；本 ADR 回答剩下的一层：**已入库的
普通条目在磁盘上的静态泄露面**——笔记本失窃、备份文件外流、其他系统用户
直接读 `state/db.sqlite`。3.4 任务要求评估 age / SQLite 加密扩展两条路线并
产出 PoC 结论，决定 v2.0 是否落地。

**核心矛盾（先于方案存在）**：本项目 2.1 引入了 FTS5 trigram 全文索引，索引
文件本身是明文内容的完整投影——**只要 FTS 索引落盘，任何"只加密数据列"的
方案都在索引上漏光**。任何加密方案必须同时回答"搜索怎么办"，不存在只加密
`clips` 表的便宜做法。

**威胁模型的诚实边界**：对已启用 LUKS/主目录加密的用户，库加密的边际收益
接近零；加密的受益者是"未启用磁盘加密、但担心单文件泄露"的用户（备份同步
到不受信介质是典型场景）。因此结论必然是 **opt-in 默认关**，而非默认安全。

## 实测（口径与复现）

**闭包口径**（唯一口径命令，见 ARCHITECTURE §9；scratch 工程 = `cargo init`
后 `cargo add` 对应依赖，单位：`cargo tree -e normal --prefix none | sed 's/ (\*)$//' | sort -u | wc -l`）：

| 配置 | 闭包 | 相对基线 |
|---|---|---|
| `rusqlite`（bundled，基线） | 28 | — |
| 基线 + `chacha20poly1305` + `argon2` | 34 | **+6** |
| `age` 0.12 单独 | 137 | **+109** |
| `rusqlite`（bundled-sqlcipher + vendored-openssl） | 12 | ≈0（替换引擎，crate 数近似） |

age 的 +109 几乎全部来自其内嵌的本地化栈（`i18n-embed`/`fluent`/`i18n-embed-fl`）。

**运行时**（release，10k 次 × 1KB 载荷，含 nonce 生成；机器为本机沙盒）：

| 指标 | ChaCha20-Poly1305 | age（x25519 静态收件人） |
|---|---|---|
| 加密 | **2.50 µs/条** | 59.19 µs/条（24×） |
| 解密 | **2.22 µs/条** | 85.97 µs/条（39×） |
| 密文开销 | **+16 字节** | +314 字节 |
| 100KB 大载荷加密 | 69.28 µs | —（无意义，同量级差） |
| argon2id 默认参数单次派生 | 22 ms（解锁一次性） | — |

**SQLCipher（整库透明加密）对照**（100k 行同构库，同机同口径）：

| 指标 | 原生 bundled SQLite | bundled-sqlcipher |
|---|---|---|
| 批量插入 100k | 0.1 s | 0.3 s（3×，绝对值仍可忽略） |
| list300（pinned/ts 索引序） | 0.06 ms | 0.06 ms（无差） |
| 库体积 | 15.4 MiB | 15.8 MiB（+2.6%） |
| release 构建时长 | — | **+69 s**（openssl-src 编 C 链） |

**FTS 兼容性**：SQLCipher 在密文库内保留 FTS（搜索零降级）；按条目方案的
密文不可索引——加密条目必须**排除出 FTS**，搜索退化为逐条解密匹配。按
`MENU_LIMIT = 300`/默认 `max_items = 750` 的真实库规模，线性解密扫描
750 × 2.2 µs ≈ **1.7 ms**，完全可接受（本项目搜索预算本就定义在 10k 口径
< 50ms）。

## 决策

1. **v2.0 落地，方案 = 按条目 AEAD**：`chacha20poly1305`（ChaCha20-Poly1305，
   AEAD，闭包 +6 crate）+ `argon2`（passphrase → argon2id 派生密钥）。
   opt-in 配置项（如 `encryption = "keyfile" | "passphrase" | "off"`，默认
   `off`），加密条目的 `text` 列存 `nonce ‖ ciphertext`（+版本前缀），图片
   数据文件整文件加密；**加密条目不入 FTS**，搜索对其走线性解密扫描。
2. **密钥管理两档**：`keyfile`——`state/secret.key`（0600，随机 32 字节，
   daemon/CLI/GUI 每次打开库时读取）；`passphrase`——每次解锁输入，
   argon2id 派生（22 ms/次，daemon 长驻只付一次）。keyfile 档的诚实定位：
   防的是"库文件单独外流"（备份/同步盘），**不防同盘攻击者**——文档必须
   写明，不许暗示 keyfile 等于强保护。
3. **本轮（v0.7）不写实现代码**：Phase 3 的交付物就是本决策；实验 flag 随
   v2.0 立项（届时需同步设计 export/import 对密文的处理——导出默认明文 +
   警示，或整包加密，属独立决策面）。

## 理由

- **闭包**：+6 crate 与 blake3 引入（+3）同量级，符合 §9 开销预算精神；
  对比之下 age 的 +109（本地化栈）对本项目"每次捕获都要过加密路径"的
  定位是纯粹的浪费——我们不需要 age 的 interop/多收件人/armor 能力
- **性能**：2.5 µs/条对捕获路径（本就被文件系统 I/O 主导，10ms 级/条）
  不可分辨；FTS 降级扫描在真实库规模下 1.7 ms，与 2.1 交付时"短查询
  LIKE 回退毫秒级"的既有取舍同构
- **SQLCipher 被拒**：构建链 +69s openssl-src（CI 代价每次都要付）、与
  `bundled` 特性互斥（引入即全项目换引擎，非 opt-in 形态）、密钥 = 整库
  一把（无法做"只加密敏感条目"的渐进路径）。查询性能与体积的实测差异
  反而可接受——**否决理由是工程面而非性能面**
- **age 被拒**：闭包 +109 与性能 24×/39× 双杀，密文膨胀 314 B/条在
  `max_clip_bytes` 限额语境下也无谓放大

## 被拒备选（其他）

- **加密 FTS 索引 / 自建加密倒排**：FTS5 无 hook 点，自建等于重写搜索引擎，
  复杂度远超收益
- **OS keyring 存密钥**（secret-service）：正是 1.8 移除 zbus 栈时 -81 crate
  的老路，闭包红线
- **默认开启加密**：LUKS 用户付成本得零收益，违背"默认轻量"

## 代价与边界（已识别，v2.0 立项时细化）

- **搜索体验**：加密开启后，加密条目不参与 FTS 相关度排序，仅子串命中
  （trigram → 解密后线性匹配的语义差异要在文档写明）
- **schema**：需 v5→v6 迁移（text 列编码版本前缀 + `encrypted` 标记列）；
  3.3 的 `wipe --sensitive` 对密文条目不可再做正则判定（密文进不了
  ignore_regex 的尺子）——加密库的敏感清除退化为全量 wipe 或按条目
  明文后判定，v2.0 设计时必须二选一并写入文档
- **导出/回灌**（ADR-004）：NDJSON 含明文的既有语义与加密互斥，处理策略
  独立决策
- **既有库迁移**：开启加密需一次性全库重写（明文 → 密文），应复用 2.2
  的"VACUUM INTO 快照 + 失败即放弃"模式
