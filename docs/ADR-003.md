# ADR-003: 文本去重指纹统一为 blake3

- 状态：已采纳（2026-09-01，任务 2.2）
- 关联：ROADMAP Phase 2 / 2.2（v1.0 硬前置）；任务 2.4（导出/回灌依赖稳定指纹）

## 背景

`clips.hash` 是去重与 ▶ 当前项标识的唯一真相源。v0.4–v0.5.2 文本指纹用
std `DefaultHasher`——标准库明确不承诺算法跨编译器/版本稳定，rustc 升级即
全体失配：daemon 捕获每条内容都会因"查不到旧 hash"重新入库（整表翻倍），
跨机器导出/回灌同理。图片侧已用稳定的 FNV-64 指纹（`image_content_key`），
文本侧属历史欠账，ROADMAP 定为 v1.0 硬前置。

## 决策

文本指纹 = `blake3(text)` 的 64 字符小写 hex（纯 hex，无算法前缀）；schema
v3→4 一次性全表重算；图片保持 `img:` 前缀 FNV 指纹不动。

## 理由

- **稳定性**：blake3 算法规范固定，跨编译器/进程/机器/年代输出一致——
  v1.0 数据可携的前提
- **碰撞面**：256 位输出，作为长期数据指纹无实际碰撞担忧
  （DefaultHasher 仅 64 位 + 长度后缀）
- **性能**：吞吐 GB/s 级，`max_clip_bytes` 限额下 hash 成本与读取同量级；
  bench 无回归（`list_300_of_10k` 1.02ms，预算 11ms）
- **开销**：default feature 仅 std，纯 Rust + 运行时 SIMD 检测，闭包
  +3 crate（blake3/constant_time_eq/cpufeatures），零构建链新增

## 被拒备选

- **继续 DefaultHasher + 升级时容忍翻倍**：翻倍在去重工具上等于数据事故，
  且每次 toolchain 升级复发；v1.0 导出/回灌彻底不可行
- **fnv1a / xxhash**：稳定但非密码学强度，64 位碰撞面随历史增长不可控；
  xxhash 依赖面与 blake3 相当，收益仅编译速度
- **SHA-256（sha2 crate）**：同为密码学稳定，但软件路径慢于 blake3 的
  SIMD 实现，无额外优势
- **`b3:` 算法前缀**：为"未来再换算法"预留演进空间，但 256 位 blake3 没有
  现实的更换需求，纯 hex 与旧格式（短 hex-长度）天然可区分，不值得为
  每行多付 3 字节

## 代价与边界（已验证/已文档化）

- **一次性迁移（v3→4，migrate.rs）**：事务（BEGIN IMMEDIATE + 事务内重读
  版本防双进程竞态）内按 blake3(text) 分组合并"同文本不同旧 hash"行
  （幸存行 = ts 最大、pinned 取 OR、image_path 继承），DELETE 经 FTS
  触发器自动同步，无需重建索引
- **快照**：迁移前 `VACUUM INTO` 至 `state/db.sqlite.pre-blake3`（固定名
  单份覆盖，用户可手动删）；快照失败即放弃迁移——宁守旧 hash，不做无退路的
  全表手术
- **指针重映射**：▶ 当前项指针存旧 hash，迁移后按 old→new 映射重写
  （best-effort，写失败不阻断）
- **防翻倍断言**：单测锁定条目数只减不增、文本行全量重算、图片指纹不动、
  FTS 同步、幂等（二次 connect 不重跑）
- **混跑窗口**：旧 daemon + 新 CLI 同时运行期间可能各按旧/新算法入库同文本
  （去重暂失效，迁移后成为下一轮"同文本不同 hash"存量）——升级应整体替换
  二进制并重启 daemon（systemd 重启后任一子命令首次运行即触发迁移）
