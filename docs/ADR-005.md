# ADR-005: ★ 条目删除确认统一为 core 单一状态机（15s TTL）

- 状态：已采纳（2026-09-10，任务 2.6 / 问题项 C1）
- 关联：ROADMAP Phase 2 / 2.6；任务 1.5（fzf 内嵌二段确认的原始实现）；
  ADR-001（原生 UI）；`crates/niri-clip-core/src/confirm.rs`

## 背景

"删除星标条目需要二次确认"这一条产品语义，在代码里长出了**三套实现**，且语义已分叉：

| 实现位置 | 机制 | 有效期 | 落盘 |
|---|---|---|---|
| `core/tui.rs` `delete_with_fzf_confirm` | `state/pending_delete`（id + 时间戳）+ `list-raw` 行尾标记 | **15s TTL** | 是 |
| `gui/update.rs` `delete_selected` | `App.confirm_delete: bool` 内存字段 | **无 TTL**（挂起态可无限期存活） | 否 |
| `cli/main.rs` `delete`（非 `--fzf`） | 现场 spawn `fuzzel --dmenu` 两选项弹窗 | 无 | 否 |

后果有三：

1. **用户可感知的行为不一致**：同一动作，fzf 版挂起 15 秒后自动作废，GUI 版挂起后去接个电话回来仍处于"再按即删"状态——后者是三者中最危险的形态。
2. **语义变更要改三处**，改一处忘两处；且这三处都不在"业务层"，UI 层被迫承载产品语义，违背 ARCHITECTURE §1 的分层约定。
3. **CLI 的 `delete` 依赖 fuzzel**：AUR 主包只装 CLI（不带 GUI），无 fuzzel 环境下 ★ 条目"删不掉"，只好加 `--force` 绕过——确认机制形同虚设。

## 决策

**在 core 建立唯一的删除确认状态机**（`crates/niri-clip-core/src/confirm.rs`），
CLI 与原生 UI 都只调用它、各自只负责"如何呈现挂起态"：

```rust
pub enum Decision { Deleted, Pending }
pub fn request(id: i64) -> Result<Decision>   // 状态机唯一入口
pub fn pending_id() -> Option<i64>            // 供 UI 呈现（含 TTL 判定与过期清理）
pub fn clear()                                // 主动作废（Esc / 选中移动 / 会话开始）
```

语义（三者统一后）：

- 非星标条目 → 立即删除，返回 `Deleted`
- 星标条目 + 无有效挂起 → 挂起（写入 `state/pending_delete`，含时间戳），返回 `Pending`
- 星标条目 + 同一 id 的有效挂起（≤15s）→ 真删并清除挂起，返回 `Deleted`
- 星标条目 + 挂起到期或指向别的 id → **重新挂起**（绝不因"挂起态陈旧"而误删）
- `--force` 仍保留，供脚本/无头环境显式绕过确认

**TTL = 15 秒**，落盘复用 `state/pending_delete`（id + 毫秒时间戳，读写皆宽容损坏）。

## 理由

- **安全方向一致**：15s 是三者中最保守的选择——它把"挂起态无限期存活"这一最危险形态消灭掉。剪贴板历史里 ★ 条目通常是用户刻意保留的内容，误删成本高于多按一次的麻烦。
- **落盘而非内存**：CLI 是"一次调用一个进程"的形态，挂起态必须跨进程存活（`Ctrl-X` → `list-raw` 重载 → 再 `Ctrl-X` 是**两个不同的进程**）。GUI 是长驻进程，但共享同一份状态可让两种前端的挂起态互相可见，行为天然一致。
- **TTL 检查放在读取侧**：`pending_id()` 判断过期即清文件，不依赖定时器；CLI 无定时器可用，GUI 也不需要为它加一个 timer。
- **去掉 CLI 的 fuzzel 弹窗**：确认语义由状态机统一后，弹窗路径不再有存在理由；顺带移除 `cli/main.rs` 里约 30 行 fuzzel 编排，并让 ★ 条目在无 fuzzel 环境也能正常走二段确认。

## 被拒备选

| 备选 | 拒因 |
|---|---|
| **保留三套实现，仅把 GUI 的 bool 改成 15s** | 只解决"分叉"的症状，不解决"三处实现"的病根；下次语义变更仍要改三处 |
| **统一为"无 TTL"（对齐 GUI 现状）** | 挂起态无限期存活，隔天误按一次即真删；对 ★ 条目这个安全方向是反的 |
| **统一为 60s TTL** | 折中方案，但"15s 够用吗"缺乏证据支持改长；现状已在 fzf 路径验证 15s 可用，不引入无依据的变量 |
| **确认态放在 UI 层（各自内存）** | 违背分层（产品语义必须在 core）；且 CLI 跨进程形态下无法实现 |
| **为状态机引入定时器/后台清理** | TTL 在读取侧判定即可，清除是"下次读到时顺手做"，无需常驻定时器 |

## 代价与边界（已验证 / 已文档化）

- **GUI 横幅可能滞后**：GUI 为避免"渲染路径上做同步 fs IO"（曾导致与光标同节奏的闪烁，见 GUI 三轮修复），
  横幅显示的是在消息路径刷新的本地镜像。因此**到达 15s 后横幅可能残留到下一次消息**。
  这不构成安全问题：**删除与否由状态机的 TTL 判定**——此时再按 `Ctrl-X` 只会重新挂起，不会删除。
- **CLI 非 `--fzf` 路径的行为变化（用户可见）**：`niri-clip delete <id>` 对 ★ 条目不再弹 fuzzel，
  改为"挂起 + 提示 15 秒内再执行一次"。提示文案与退出码在实现中固定并测试锁定。
- **单文件状态**：同时只允许一个挂起目标；对另一个 ★ 条目发起确认会**转移**挂起目标（与 1.5 的既有语义一致）。
- **测试**：原 `tui.rs` 的 TTL 全流程测试迁入 `confirm.rs` 并扩充——覆盖非星标直删、星标两段、过期重新挂起、
  挂起目标转移、损坏状态文件。CLI 提示文案的行为由 `store_tests`/`confirm` 侧锁定。
